# Chapter 6: Conclusion

## 6.1 Introduction

This chapter presents the final conclusion of the SecureVote blockchain voting system project. It summarises the system strengths, acknowledges the limitations encountered during development, identifies future improvements that can extend the platform's capabilities, provides a critical summary of the project outcomes, and closes with the final conclusion. The chapter reflects on the extent to which the project objectives defined in Chapter 1 were achieved and evaluates the system against the functional and non-functional requirements specified in Chapter 3.

SecureVote was developed as a mobile-based electronic voting platform that combines identity verification through KYC, secure ballot casting with cryptographic receipts, public receipt verification, and blockchain anchoring through a Solidity smart contract on the Polygon Amoy testnet. The system was implemented across three codebases: a Flutter mobile application with 47 screens for voters, a Next.js 16 web portal with 17 admin pages for administrators and verifiers, and a Cloudflare Workers backend API with Hono, D1, R2, and KV. The final system supports the complete voting workflow from voter registration through OTP verification, KYC submission and admin review, election browsing, vote casting with duplicate prevention, receipt generation with QR codes, blockchain anchoring with Merkle roots, and public receipt verification without revealing voter identity.

The project was developed over 16 weeks using the Agile Scrum methodology, with two phases of eight weeks each and four two-week sprints per phase. Each sprint produced a testable increment, and the system was continuously tested through unit testing (10 test cases), system testing (5 end-to-end scenarios), integration testing (12 test cases), and acceptance testing (13 test cases). All tests passed, and the system is deployed and operational at the production Cloudflare URLs.

## 6.2 System Strengths

Several strengths distinguish SecureVote from traditional voting systems and simpler electronic voting prototypes. These strengths span the architecture, security model, user experience, and transparency mechanisms.

**Cross-Platform Mobile Application.** The Flutter framework enables a single codebase to target both Android and iOS devices. This reduces development effort and ensures a consistent user experience across platforms. The mobile application includes 47 screens covering authentication, KYC, election browsing, voting, receipts, and profile management. The use of Provider for state management and Dio with a custom interceptor for API communication ensures that the app is responsive, handles token refresh transparently, and provides a smooth user experience.

**Strong Identity Verification.** The KYC workflow requires voters to upload identity documents and a selfie photo before they can cast a vote. This reduces the risk of impersonation and duplicate accounts. The review process is handled by administrators through the web portal, and documents are stored securely in Cloudflare R2 with access controlled by the backend. Every document access is audit-logged, and the voter's KYC status is enforced at the voting endpoint with a 403 response if the status is not `approved`.

**Anti-Double-Vote Enforcement.** Duplicate voting is prevented at two levels. At the application level, the voting endpoint pre-checks whether the voter has already voted in the election. At the database level, a `UNIQUE(election_id, user_id)` constraint on the `votes` table provides a hard guarantee that no duplicate vote can be stored, even if the application layer check is bypassed. This two-layer approach provides robust protection against duplicate vote submission and ensures that each verified voter can cast exactly one vote per election.

**Cryptographic Receipts and Public Verification.** Every vote produces a unique receipt ID in the format `SV-XXXX-XXXX-XXXX-XXXX` and a SHA-256 vote hash computed from the election ID, user ID, selections, receipt ID, timestamp, and nonce. The public verifier endpoint allows anyone to confirm that a receipt exists and was included in the final election record without revealing the voter's identity or ballot selections. This supports transparency while preserving ballot secrecy, which is a fundamental requirement of any voting system.

**Blockchain Anchoring.** The system computes a Merkle root from all vote hashes in an election and anchors it to the Polygon blockchain through a Solidity smart contract. The `finalize` function posts the Merkle root on-chain, creating a tamper-evident record that can be verified independently using a blockchain explorer. The `commitVote` function allows individual vote hashes to be anchored on-chain in real time, and a Cloudflare cron listener picks up missed events as a backup. The smart contract was tested with 5 Hardhat test cases, all passing, and deployed to the Polygon Amoy testnet for the FYP demonstration.

**Audit Log Hash Chain.** Every privileged action (election creation, status transition, KYC review, document access, vote casting) is recorded in an audit log with a SHA-256 hash chain. Each entry stores `prev_hash` (the hash of the previous entry) and `entry_hash` (the hash of the current entry's content). The verification endpoint walks the chain and detects any tampering, returning the ID of the first broken entry. This provides strong accountability for administrative actions and ensures that the audit trail cannot be silently modified.

**Edge-First Architecture.** The backend runs on Cloudflare Workers, with data stored in D1 (SQLite at the edge), files in R2, and sessions in KV. This architecture scales automatically, requires no server maintenance, and keeps the deployment cost low for the FYP scope. Workers run in data centres close to users, providing low latency for API requests. The serverless model means that the system only consumes resources when handling requests, making it cost-effective for elections that have bursty traffic patterns.

**PBKDF2 Password Hashing.** Passwords are hashed using PBKDF2-SHA256 with 100,000 iterations and a 16-byte random salt via the Web Crypto API. This is an industry-standard key derivation function that is resistant to brute-force and rainbow table attacks. The high iteration count makes each hashing operation computationally expensive, slowing down any attacker who might obtain the password hashes. The use of the Web Crypto API ensures that the hashing runs natively on Cloudflare Workers without Node.js polyfills.

**Rate Limiting and Brute Force Protection.** Authentication endpoints are rate-limited at 5 attempts per 15 minutes per identifier (email or IP) using Cloudflare KV. This prevents brute-force attacks on login, registration, and OTP verification. OTP emails are also rate-limited to 3 sends per email per hour, preventing email flooding. Exceeding the rate limit produces a 429 response with a clear error message.

**Type Safety Across the Stack.** The backend and web portal are written in TypeScript with strict mode enabled and no `any` types. The Flutter app is written in Dart with sound null safety. Type checking (`tsc --noEmit` for backend and web, `flutter analyze` for mobile) passes with zero errors, catching potential runtime issues at compile time. The use of Zod for runtime schema validation provides an additional layer of type safety at the API boundary, ensuring that request bodies match the expected types before reaching the business logic.

**Structured Error Handling.** The backend returns structured error responses using the `application/problem+json` media type with error codes and descriptions. The Flutter app parses these through a Dio interceptor that converts errors into typed `ApiError` objects. The web portal uses a typed API client that handles loading, error, and empty states uniformly. This ensures that errors are consistently communicated to the user and can be programmatically handled by the client applications.

## 6.3 System Limitations

Despite the strengths, several limitations were identified during development and testing. These limitations are acknowledged to provide an honest assessment of the system's current state and to guide future work.

**Limited Automated Test Coverage.** The project currently relies on manual end-to-end testing and static analysis (`flutter analyze`, `tsc --noEmit`). While the unit, system, integration, and acceptance tests described in Chapter 5 were all executed and passed, a comprehensive automated test suite covering unit tests for the backend Merkle engine and vote service, widget tests for the Flutter app, and Playwright end-to-end tests for the web portal is planned for future work. The current test suite is sufficient for the FYP scope but would need to be expanded for production use. A GitHub Actions CI/CD pipeline is documented but not yet enabled.

**Blockchain Deployment on Testnet.** The smart contract is deployed on the Polygon Amoy testnet, which is free but does not provide the same security guarantees as a production mainnet deployment. Testnet tokens have no economic value, which means that the security model relies on the Polygon mainnet's economic incentives (proof-of-stake) for true tamper resistance. The testnet is appropriate for the FYP demonstration, but a production system would require mainnet deployment and economic security considerations, including the cost of gas for each transaction and the reliability of the RPC provider.

**Simulated KYC Document Verification.** For the FYP, the KYC document is uploaded by the voter and reviewed by an admin. The system does not integrate with a third-party identity verification provider (such as Persona, Onfido, or Veriff) that could perform automated liveness checks, document authenticity validation, and anti-spoofing detection. The current manual review process is sufficient for small-scale elections but would not scale to large voter populations where automated verification is needed to handle high volumes within a reasonable timeframe.

**No Real-Time Push Notifications.** Notifications are delivered through email (via the Resend API) and in-app polling (the `NotificationsProvider` polls every 30 seconds while the app is in the foreground). Native push notifications using Firebase Cloud Messaging for Android or Apple Push Notification Service for iOS are not yet integrated. This limits the immediacy of status updates on mobile devices when the app is in the background or closed. For critical notifications like KYC approval or election opening, push notifications would be more appropriate.

**Web Build for Flutter App.** The Flutter web build cannot be produced with the current `flutter_secure_storage_web` dependency because it uses the deprecated `dart:html` API, which is not compatible with the current Flutter web compiler. The FYP demo uses Android builds, and a web-compatible token store (e.g., an IndexedDB wrapper or a different secure storage plugin) would be needed for a future web version of the voter app. This limitation does not affect the Android or iOS builds, which are the primary targets for a voting application.

**iOS Device Deployment.** While the Flutter source compiles for iOS, real device deployment requires an Apple Developer account (USD 99 per year) and a provisioning profile, which is out of scope for the FYP budget. Android was the primary target platform for testing and demonstration. The iOS build was verified to compile successfully but was not tested on a physical iOS device. A production deployment would require an Apple Developer account and TestFlight distribution for beta testing.

**Forgot Password and Reset Password.** The backend does not yet implement forgot-password and reset-password endpoints. The Flutter app shows a clear "not yet available" notice on the login screen's forgot password link. This is a standard authentication feature that would be needed for production use, and its absence is a limitation of the current implementation. The implementation would require a password reset token flow with email verification.

**Scalability Under High Load.** While Cloudflare Workers scale automatically, the D1 database has per-database query limits that could become a bottleneck under very high concurrent load (e.g., thousands of votes cast simultaneously in a large-scale election). The system has not been load-tested under such conditions. For production use with large voter populations, read replicas, query batching, and potentially a different database tier would be needed to handle the write-heavy workload of concurrent vote casting.

## 6.4 Future Work

Several improvements and extensions are planned for future releases of SecureVote. These improvements address the limitations identified above and extend the system's capabilities for production use.

**Production-Grade KYC Integration.** Replace manual admin review with a third-party identity verification provider (Persona, Onfido, or Veriff) that performs automated document verification, facial recognition, and liveness detection. This would improve security, reduce the administrative burden, and enable the system to handle large voter populations efficiently. The backend contract already supports this integration through the multipart upload endpoint and the KYC status fields; the implementation would involve adding a webhook endpoint for the provider to call back with verification results and updating the admin KYC queue to show provider-provided metadata alongside the manual review interface.

**Push Notification Service.** Integrate Firebase Cloud Messaging (FCM) for Android and Apple Push Notification Service (APNS) for iOS to deliver real-time alerts for KYC status changes, election openings, vote confirmations, and election result publications. The Flutter app would use the `firebase_messaging` package to register for push notifications and handle incoming messages. The backend would send notifications through FCM in addition to the existing email and in-app channels. This would require adding a `fcm_token` field to the `users` table and an endpoint for the app to register and update its token.

**Polygon Mainnet Deployment.** Migrate the smart contract from the Amoy testnet to the Polygon mainnet for production use, providing stronger security guarantees and permanent on-chain anchoring. This would require a funded wallet with MATIC tokens for gas, a reliable RPC provider (e.g., Infura or Alchemy), and monitoring of transaction costs. The smart contract code would not need changes, but the deployment and interaction scripts would need to be updated with the mainnet RPC URL and contract address. Gas cost optimisation (minimising the number of on-chain transactions per election) would become a design consideration.

**Comprehensive Automated Testing.** Implement unit tests for the backend Merkle engine, vote service, and authentication functions using the Cloudflare Workers test environment (`@cloudflare/vitest-pool-workers`). Implement widget tests for the Flutter app using the Flutter test framework, covering at least the critical screens (login, ballot, receipt). Implement Playwright end-to-end tests for the web portal, covering the admin workflows (login, election creation, KYC review, audit verification) and the public verifier. A GitHub Actions CI/CD pipeline should be enabled to run these tests automatically on every commit and pull request, blocking merges on test failure. The target coverage is 60 percent on the data and domain layers.

**Forgot Password and Reset Password.** Implement the forgot-password and reset-password flow: the user requests a reset, the backend generates a time-limited reset token (JWT with a short expiry and a specific `purpose` claim), sends it via email, and the user submits a new password with the token. The reset endpoint would revoke all existing sessions for the user. This is a standard authentication feature and would complete the authentication module.

**Multi-Language and Accessibility Support.** Add support for multiple languages starting with Malay and English, using Flutter's `intl` package for the mobile app and `next-intl` for the web portal. Conduct an accessibility audit to meet WCAG 2.1 AA standards, including screen reader support, keyboard navigation, colour contrast, and form labels. This would make the system more inclusive for diverse voter populations, including elderly voters and voters with disabilities.

**Offline Mode and Sync.** Allow voters to view past elections and receipts offline, with automatic synchronisation when connectivity returns. The Flutter app would cache election data and receipts locally using `sqflite` or `hive`, and sync with the backend when the network is available. This would improve the user experience in areas with unstable network coverage, which is relevant for rural voters or voters in areas with poor mobile data connectivity.

**Advanced Analytics and Reporting.** Expand the admin dashboard with turnout predictions (based on early voting patterns), demographic breakdowns (where legally permitted), and automated PDF election reports generated at election close. The reporting module would use a server-side PDF generation library to produce official election result documents with the Merkle root and blockchain anchor included for verification. These features would help election administrators analyse participation and improve future elections.

**Multi-Election and Recurring Elections.** Support recurring elections (e.g., annual board elections) that reuse voter rolls and candidate templates, and support multi-phase elections (e.g., primary and general) where the results of one phase determine the candidates in the next. This would extend the election data model with a `parent_election_id` field and update the election management UI to support creating linked elections.

**Decentralised Identity Integration.** Integrate a decentralised identity solution (such as Polygon ID or Ethereum Attestation Service) to allow voters to prove their identity without uploading documents to a centralised server. This would enhance privacy by allowing the system to verify that a voter is a unique human without storing their identity documents. The verifier would issue a zero-knowledge proof of identity that the voter stores in their wallet and presents at registration. This is a longer-term enhancement that aligns with the blockchain focus of the project.

## 6.5 Critical Summary

SecureVote was developed to address several problems with traditional voting systems: the risk of tampering with centralized electronic voting databases, the lack of transparency in vote counting, the difficulty of verifying that a vote was counted, and the barriers to participation created by in-person voting requirements. The project demonstrates how blockchain technology, cryptographic receipts, mobile applications, and edge-native infrastructure can be combined to create a voting system that is secure, transparent, and accessible.

The project achieved its primary objectives as defined in Chapter 1. The cross-platform mobile application was implemented with 47 screens covering the complete voter journey from registration to receipt verification. The secure identity verification workflow was implemented with KYC document upload, admin review, and status enforcement at the voting endpoint. The transparent vote verification system was implemented with cryptographic receipts, a public verifier endpoint, and Merkle proof generation. The blockchain-based result anchoring was implemented with a Solidity smart contract on Polygon Amoy, a Merkle tree engine, and a cron listener for backup event syncing.

The system architecture provides a clear separation of concerns. The Flutter mobile app handles the voter-facing presentation layer. The Next.js web portal handles the admin and verifier presentation layer. The Cloudflare Workers backend handles the business logic and data layer. The Polygon blockchain handles the tamper-evident record layer. This separation allows each subsystem to be developed, tested, and deployed independently, and it aligns with modern cloud-native and edge-native architecture practices (Newman, 2021; Kleppmann, 2017).

The Agile methodology proved effective for managing the project's complexity and iterative requirements. The 16-week schedule with two-week sprints allowed the project to adapt to changing requirements and technical challenges. The testable increment at the end of each sprint ensured that the system was continuously functional and that regressions were caught early. The use of type checking as a pre-commit gate prevented type-related bugs from entering the codebase.

The testing results (10 unit tests, 5 system testing scenarios, 12 integration tests, and 13 acceptance tests, all passing) provide confidence that the system meets its functional requirements. The data acceptance testing confirmed that user input is correctly validated and stored, with no data loss, duplication, or corruption observed. The system demonstrated high data accuracy with an acceptance rate of approximately 99 percent for valid data.

While several limitations remain, particularly around automated test coverage, third-party KYC integration, push notifications, and mainnet blockchain deployment, the system provides a solid foundation for future development. The architecture is designed to accommodate these enhancements without requiring fundamental restructuring. The backend's modular route structure, the blockchain wrapper's graceful degradation pattern, and the mobile app's feature-based directory organisation all support incremental extension.

The project contributes to the field of electronic voting by demonstrating a practical implementation that combines blockchain anchoring for tamper-evidence, cryptographic receipts for voter-verifiability, edge-native infrastructure for performance, and mobile technology for accessibility. The system shows that it is feasible to build a voting platform that gives voters confidence their vote was counted, gives administrators tools to manage elections efficiently, and gives observers the ability to verify results independently.

## 6.6 Conclusion

SecureVote successfully demonstrates a practical blockchain-based electronic voting system designed to address the limitations of traditional voting methods. The project achieved its primary objectives: a cross-platform mobile voting application with 47 screens, secure identity verification through KYC with document upload and admin review, transparent vote verification through cryptographic receipts and a public verifier endpoint, and blockchain-based result anchoring through a Solidity smart contract on the Polygon Amoy testnet with Merkle root computation.

The system was implemented using modern technologies including Flutter 3.x for the mobile app, Next.js 16 with React 19 and Tailwind CSS 4 for the web portal, Cloudflare Workers with Hono, D1, R2, and KV for the backend API, Solidity 0.8.24 for the smart contract, and Polygon Amoy for blockchain deployment. The implementation was tested through unit testing (10 test cases), system testing (5 end-to-end scenarios), integration testing (12 test cases), and acceptance testing (13 test cases), all passing.

The Agile methodology proved effective for managing the project's complexity and iterative requirements over the 16-week development period. The three-tier architecture provides a clear separation of concerns between the presentation, application, and data layers, and the use of edge-native Cloudflare services reduces operational overhead while providing low-latency global access. The security model, combining PBKDF2 password hashing, JWT authentication with role-based access control, rate limiting, Zod schema validation, database constraints, and audit logging with hash chain verification, provides multiple layers of protection against common attack vectors.

While several limitations remain, particularly around automated test coverage, third-party KYC integration, push notifications, and mainnet blockchain deployment, the system provides a solid foundation for future development. With the planned future enhancements, the platform has the potential to support real-world elections in educational institutions, corporate governance, and community organisations. The project demonstrates that blockchain technology, cryptographic receipts, and mobile applications can be combined to create a voting system that is secure, transparent, and accessible.
